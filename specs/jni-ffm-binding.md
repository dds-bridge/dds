# JVM Binding (Foreign Function & Memory)

> **Specs vs. doxygen / docs.** How to build, call, and publish the JVM binding is
> in `docs/jni_interface.md`; the self-contained shared-library rationale is also
> spelled out in comments in `jni/BUILD.bazel`. This spec records the
> cross-cutting contracts: the ABI boundary, the packaging model, and the
> invariants the tests enforce.

## Purpose

This capability lets Java call the solver with no hand-written JNI C/C++ glue. It
ships two things: a single self-contained native shared library that exports the
stable C ABI, and hand-written Foreign Function & Memory (Project Panama) bindings
that downcall into it. It exists so JVM consumers get the solver as an ordinary
Maven dependency with the native library embedded in the jar. It binds the pure-C
shim from [dds-public-api](dds-public-api.md), not the C++ API.

## Behaviour & invariants

> Class/method detail is in `Dds.java` and `docs/jni_interface.md`; these are the
> whole-binding guarantees.

- **One self-contained native library.** `//jni:dds_shared` (`cc_shared_library`)
  links every internal sub-library statically so `System.loadLibrary("dds")`
  needs exactly one file. Per-OS name: `dds.dll` / `libdds.dylib` / `libdds.so`.
  On Unix the export set is the stable C ABI (`dll.h` + `dds_c_*`); on Windows
  it is broader — see the next bullet.
- **The exported ABI is pinned by checked-in export lists on Unix.** Linux links
  with `version_script.lds` (`-Wl,--version-script`), macOS with
  `exported_symbols.lds` (`-Wl,-exported_symbols_list`). Those `.lds` files are
  the **source of truth** for the stable binding symbol set (`dll.h` +
  `dds_c_api.h`) and are regenerated by `gen_export_lists.py` after header
  changes. Sync is enforced by `//jni/tests:export_set_test`; the generator's
  parser is unit-tested by `gen_export_lists_test`. **Windows has no `.lds`
  branch:** the DLL exports whatever is marked `DLLEXPORT`, which is a
  **superset** of the Unix list (it also includes the modern `dds_*` context API
  from `dds_api.hpp`). See [dds-public-api](dds-public-api.md).
- **Bindings are hand-written, not jextract-generated.** `//jni:dds_ffm`
  (`java_library`, `java/org/dds/ffm/Dds.java`) declares the struct
  `MemoryLayout`s and `Linker` downcall handles for the `dds_c_*` shim plus
  `GetDDSInfo`. Requires **JDK 22+** (`java.lang.foreign` is stable there, no
  `--enable-preview`); the Bazel build supplies a hermetic JDK via `rules_java`,
  so no system JDK is needed. Callers must pass `--enable-native-access`.
- **Native-in-jar packaging is per-triplet and host-only (Phase 1).** `copy_file`
  targets `native_in_jar_<os>_<arch>` stage `dds_shared` under
  `native/<os>-<arch>/<libname>`, gated by `target_compatible_with`. The embedded
  path's arch must match what `Dds.loadEmbedded()` resolves from `os.arch` at
  runtime — so the arch is part of the build config, not hardcoded. Only the host
  triplet is built; a multi-arch fat jar is a deliberate follow-up.
- **`dds_ffm_dist` is the publishable Maven artifact.** `java_export`
  (`org.dds:dds-ffm:<DDS_FFM_VERSION>`, currently `3.0.1`) bundles the binding
  classes (exported, not recompiled) plus the host's embedded native resource, and
  generates the runnable `//jni:dds_ffm_dist.publish` target (supports a local
  `file://` `~/.m2`). On a non-listed platform the target is *incompatible*
  (skipped by `//...`) rather than a hard failure, so it never poisons unrelated
  builds.
- **Version single-sourcing is checked.** `DDS_FFM_VERSION` is kept in sync with
  `MODULE.bazel`; `dds_ffm_embedded_smoke_test` cross-checks the coordinate's
  major.minor against the embedded library's `GetDDSInfo` so a published jar can't
  misrepresent its version.
- **Two smoke tests guard the two load paths.** `dds_ffm_smoke_test` loads
  `dds_shared` directly (via `-Ddds.library.path`) and solves a known deal;
  `dds_ffm_embedded_smoke_test` loads via `Dds.loadEmbedded()` from the jar
  resource. Both smoke tests and `export_set_test` are
  `target_compatible_with`-excluded on Windows. `jar_self_contained_test` is
  not Windows-excluded; it inherits `dds_ffm_dist`'s platform compatibility.

## Key entry points

- `jni/BUILD.bazel` — `dds_shared`, `dds_ffm`, `native_in_jar_*`, `dds_ffm_dist`,
  and the smoke tests; `DDS_FFM_VERSION`.
- `jni/java/org/dds/ffm/Dds.java` — the FFM binding (layouts, downcall handles,
  `loadEmbedded()`); `DdsStatus.java` is part of the same `dds_ffm` library.
- `jni/{version_script.lds,exported_symbols.lds,gen_export_lists.py}` — the ABI
  export lists and their generator.
- Consumer guide: `docs/jni_interface.md`; packaging notes also in `jni/BUILD.bazel`.
- Guarded by `//jni/tests:{export_set_test,gen_export_lists_test,jar_self_contained_test}`
  and `//jni:{dds_ffm_smoke_test,dds_ffm_embedded_smoke_test}`.

## Known gaps / non-goals

- **No multi-arch fat jar yet** — the published jar embeds only the build host's
  native library (Phase 1).
- **No idiomatic high-level Java API** — `Dds` exposes thin typed wrappers over
  MethodHandles for the C shim; a richer convenience layer is a follow-up (see
  "Not yet supported" in `docs/jni_interface.md`).
- Windows is buildable; smoke tests and `export_set_test` are excluded there.
  `jar_self_contained_test` follows `dds_ffm_dist` compatibility instead.
- Threading follows the C shim: one solver-context handle per thread (see
  [solver-context](solver-context.md)).
